
# Requirements — Interview Preparation Coach (MCQ + Essay + Scoring)

## 1. Feature Summary

Extends the existing **Interview Preparation Coach** capability
(`src/services/interview_service.py`) so that, in addition to generating
interview topics and practice questions for a selected job, it can:

1. Generate two types of practice questions: **MCQ** (multiple choice) and
   **Essay** (open-ended, free-text).
2. Accept the candidate's submitted answers.
3. Score the submission and return **structured, role-relevant feedback**.
4. Persist both the correct answer and the candidate's answer in a single
   JSON structure per question, so scoring is a straightforward comparison
   rather than a re-derivation of "what was correct."

This is a requirements/design document only — no code changes should be made
until this is reviewed and approved. `src/services/*` logic is not to be
rewritten; new scoring/grading logic is additive (new functions or a new
module), following the existing service's patterns.

---

## 2. Goals / Non-Goals

**Goals**
- Support both MCQ and essay questions in the same practice session.
- Store, per question, both the reference ("true") answer and the
  candidate's submitted answer in one JSON object, so grading never has to
  re-fetch or re-derive the correct answer separately.
- Produce a final numeric score (and per-question feedback) at the end of
  the session.
- Keep MCQ scoring deterministic (no LLM call needed) and essay scoring
  LLM-assisted but structured (Pydantic-validated output, not free text).

**Non-Goals (for this phase)**
- No adaptive difficulty (question difficulty does not change based on
  live performance) — can be a future iteration.
- No voice/audio interview simulation — text-only for now.
- No proctoring / anti-cheating detection.

---

## 3. Question Generation Input: Track + Skill Gaps

Question generation must be driven by two inputs, not just the raw
`job_id`:

- **`track`** — the candidate's career track/field (e.g., "Backend
  Development", "Data Analysis", "Product Design"). This scopes the general
  domain of questions so they stay relevant to the kind of role the
  candidate is pursuing, even across multiple similar jobs.
- **`skillGaps`** — the specific missing/weak skills identified for this
  candidate relative to the selected job (the same gap data already
  produced by the matching/recommendation services, e.g.
  `matching_service.calculate_match` / `recommendation_explanation`).
  Each gap should map to one or more generated questions so the practice
  session is *personalized*, not generic — the candidate is quizzed
  specifically on what they're weakest in.

This means the question generation call should take a payload like:

```json
{
  "user_id": "user_456",
  "job_id": "job_123",
  "track": "Backend Development",
  "skill_gaps": ["Database Design", "REST APIs", "System Design"]
}
```

- The Coach should aim to distribute questions across `skill_gaps` (e.g.,
  1–2 questions per gap) rather than clustering all questions on a single
  skill.
- `track` acts as a filter/guide on tone and depth (e.g., a "Backend
  Development" track skews questions toward architecture/APIs/data over
  UI-focused questions), even when two skill gaps could otherwise apply to
  multiple tracks.
- If `skill_gaps` is empty (candidate already matches well), fall back to
  general track-appropriate questions rather than failing.
- `skill_tag` on each generated question (§5.1) must be set from the
  matching entry in `skill_gaps`, so the Evaluation Result (§5.3) can later
  be aggregated by skill — showing the candidate not just an overall score,
  but which specific gap areas improved or still need work.

## 4. Question Types

### 4.1 MCQ (Multiple Choice)
- 1 prompt, 3–5 options, exactly 1 correct option.
- Scored deterministically: correct = full points, incorrect = 0.
- Optionally weighted by `difficulty` (e.g., easy = 1pt, medium = 2pt, hard = 3pt).

### 4.2 Essay (Open-Ended)
- 1 prompt, no options.
- Has a `reference_answer` (the "true"/ideal answer or grading rubric —
  not shown to the candidate) used only for evaluation.
- Scored on a 0–100 scale per question, using an LLM grading call against
  the `reference_answer` and a fixed rubric (see §6.2).

Both types share: `id`, `type`, `prompt`, `skill_tag`, `difficulty`,
`related_job_id`.

---

## 5. Data Model / JSON Schemas

### 5.1 Question Object (generated by the Coach)

```json
{
  "id": "q_001",
  "type": "mcq",
  "prompt": "Which HTTP status code indicates a successful POST that created a resource?",
  "skill_tag": "REST APIs",
  "difficulty": "easy",
  "related_job_id": "job_123",
  "options": [
    { "id": "a", "text": "200 OK" },
    { "id": "b", "text": "201 Created" },
    { "id": "c", "text": "204 No Content" },
    { "id": "d", "text": "301 Moved Permanently" }
  ],
  "correct_option_id": "b"
}
```

```json
{
  "id": "q_002",
  "type": "essay",
  "prompt": "Explain the difference between optimistic and pessimistic locking in a database, and give a scenario where you'd choose one over the other.",
  "skill_tag": "Database Design",
  "difficulty": "medium",
  "related_job_id": "job_123",
  "reference_answer": "Optimistic locking assumes conflicts are rare and checks for conflicts at commit time (e.g., via a version column)... Pessimistic locking locks the row/resource upfront to prevent concurrent modification... Choose optimistic when contention is low and throughput matters; pessimistic when contention is high and correctness under conflict is critical.",
  "grading_criteria": [
    "Correctly defines optimistic locking",
    "Correctly defines pessimistic locking",
    "Gives a coherent scenario for choosing one over the other"
  ]
}
```

> `correct_option_id` (MCQ) and `reference_answer` / `grading_criteria`
> (essay) must never be sent to the client/UI before the candidate submits
> an answer — only after scoring, if feedback reveals them.

### 5.2 Submission Object (the JSON containing candidate answer + true answer)

This is the single JSON structure the scoring function consumes — it pairs
each question's reference data with what the candidate actually submitted,
so evaluation is a direct comparison with no extra lookups.

```json
{
  "session_id": "sess_789",
  "user_id": "user_456",
  "job_id": "job_123",
  "answers": [
    {
      "question_id": "q_001",
      "type": "mcq",
      "correct_option_id": "b",
      "submitted_option_id": "a"
    },
    {
      "question_id": "q_002",
      "type": "essay",
      "reference_answer": "Optimistic locking assumes conflicts are rare...",
      "grading_criteria": [
        "Correctly defines optimistic locking",
        "Correctly defines pessimistic locking",
        "Gives a coherent scenario for choosing one over the other"
      ],
      "submitted_answer": "Optimistic locking checks at the end if something changed, pessimistic locking locks it before you start editing. You'd use pessimistic locking for something like a banking transaction."
    }
  ]
}
```

### 5.3 Evaluation Result Object (output of scoring)

```json
{
  "session_id": "sess_789",
  "per_question": [
    {
      "question_id": "q_001",
      "type": "mcq",
      "is_correct": false,
      "points_earned": 0,
      "points_possible": 1,
      "feedback": "The correct answer is 201 Created, since a successful POST that creates a resource returns 201, not 200."
    },
    {
      "question_id": "q_002",
      "type": "essay",
      "score": 78,
      "points_possible": 100,
      "criteria_met": [
        "Correctly defines optimistic locking",
        "Correctly defines pessimistic locking"
      ],
      "criteria_missed": [
        "Gives a coherent scenario for choosing one over the other"
      ],
      "feedback": "Good grasp of both concepts. To strengthen this answer, add a concrete scenario explaining when you'd pick pessimistic over optimistic locking, e.g., high-contention financial transactions."
    }
  ],
  "overall_score": {
    "raw_points": 78,
    "max_points": 101,
    "percentage": 77.2
  },
  "summary_feedback": "Strong on database concepts overall; review REST status codes and practice giving applied examples in essay answers."
}
```

## 6. Scoring Logic

### 6.1 MCQ Scoring (deterministic, no LLM call)
- `is_correct = (submitted_option_id == correct_option_id)`.
- `points_earned = points_possible if is_correct else 0`.
- `points_possible` derived from `difficulty` weighting (configurable;
  default: easy=1, medium=2, hard=3).
- Feedback is templated, not LLM-generated: state the correct option and a
  one-line reason drawn from the question's own content.

### 6.2 Essay Scoring (LLM-assisted, structured output)
- Input to the grading call: `prompt`, `reference_answer`,
  `grading_criteria`, `submitted_answer`.
- Output must be **Pydantic-validated structured output** (same pattern as
  the `suggested_prompts` feature's `SuggestedPromptsSchema`), not free text —
  e.g. an `EssayGradingSchema` with `score` (0–100), `criteria_met` (list),
  `criteria_missed` (list), `feedback` (string).
- A fixed rubric prompt should instruct the model to grade **only** against
  `grading_criteria` and `reference_answer`, not general writing quality,
  to keep scoring consistent across candidates.
- **Fallback:** if the grading call fails or times out (same
  timeout+fallback pattern as `suggested_prompts/fallback.py`), return a
  neutral default (e.g., `score: null`, `feedback: "Grading unavailable,
  please retry"`) rather than blocking the whole session's results.

### 6.3 Overall Score
- `raw_points` = sum of `points_earned` (MCQ) + `score` (essay, scaled to
  the same point system or kept as a weighted percentage — decide one
  convention and apply consistently).
- `percentage` = `raw_points / max_points * 100`.
- `summary_feedback`: one short paragraph, generated after all questions
  are scored, summarizing strengths and the top 1–2 areas to improve
  (can reuse the same fast-model + fallback pattern as essay grading).

## 7. API Surface (proposed)

| Endpoint | Method | Purpose |
|---|---|---|
| `/interview/prep/generate` | POST | Generate a set of MCQ + essay questions for a `job_id`, driven by `track` and `skill_gaps` (§3) — extend the request/response to include these fields plus the `type` field and both question shapes above. |
| `/interview/prep/submit` | POST | Accept a **Submission Object** (§5.2) and return an **Evaluation Result** (§5.3). |
| `/interview/prep/sessions/{session_id}` | GET | Retrieve a past session's questions + evaluation result (for history/review). |

`submit` should be synchronous if grading is fast enough (MCQ is instant;
essay grading is the bottleneck) — apply the same timeout+fallback pattern
used elsewhere so the endpoint always returns within a bounded time even if
essay grading is slow.

---

## 8. Persistence

- Store the **Submission Object** and **Evaluation Result** together per
  session (e.g., a `interview_sessions` table/collection with
  `session_id`, `user_id`, `job_id`, `track`, `skill_gaps`,
  `questions_json`, `answers_json`, `evaluation_json`, `created_at`).
- Persisting `track` and `skill_gaps` alongside the session lets later
  features (e.g., the Roadmap Agent) query "how has this candidate scored
  on skill X across past interview sessions?" without re-parsing the
  question JSON.
- Storing the full JSON (not just a score) preserves the reference answer,
  the candidate's answer, and the feedback together — useful for the
  candidate to review later and for auditing grading quality.

---

## 9. Edge Cases to Handle

- Candidate submits no answer for a question → treat as incorrect (MCQ) /
  score 0 with feedback "No answer submitted" (essay).
- Candidate submits an `submitted_option_id` that doesn't match any real
  option → treat as incorrect, log as a possible client bug.
- Essay answer is empty or nonsensical (e.g., random characters) → grading
  call should still return a low score with feedback, not crash; consider
  a pre-check (min length) before calling the LLM to save cost.
- Essay grading call fails/times out → use fallback (§6.2), never block or
  fail the whole session.
- Mixed session with 0 essay questions → skip essay-grading step entirely,
  no wasted LLM calls.

---

## 10. Definition of Done

- [ ] Question generation is driven by `track` and `skill_gaps`, not just
      `job_id` (§3), with questions distributed across the given gaps.
- [ ] Question generation returns both MCQ and essay types, following the
      schemas in §5.1.
- [ ] `correct_option_id` / `reference_answer` / `grading_criteria` are
      never exposed to the client before submission.
- [ ] MCQ scoring is fully deterministic and requires no LLM call.
- [ ] Essay scoring uses a Pydantic-validated structured output schema, not
      raw text parsing.
- [ ] Essay scoring has a timeout + fallback so grading failures never
      break the overall session result.
- [ ] Evaluation Result includes per-question feedback and an overall
      score/percentage.
- [ ] Full session (questions + submitted answers + evaluation) is
      persisted for later review.
- [ ] No logic inside `src/services/*` is rewritten — new scoring/grading
      code is additive, following the existing service's style.
